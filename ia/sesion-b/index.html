¿Qué le falta a un chat para consultar una matrícula?

Antes de seguir: ¿qué es un harness?

  • El harness es el programa que rodea al modelo y hace todo lo que el modelo no puede hacer por sí solo
  • Arma el contexto que se le envía, ejecuta las herramientas que el modelo pide y devuelve los resultados
  • Analogía: el modelo es el motor; el harness es el vehículo que lo conecta con el mundo
  • Lo verá en detalle en el Acto 6. Por ahora basta con una idea: el modelo pide, el harness actúa
Definición mínima antes del tool call. Ejemplos de harness: Claude Code, GitHub Copilot, Cursor. En el Acto 6 se amplía (permisos, memoria, compactación).

Tool call: el modelo pide, no ejecuta

{
  "tool": "consultar_matricula",
  "arguments": { "carnet": "B12345" }
}

El modelo escribe una solicitud estructurada. Quien la ejecuta y devuelve el resultado al contexto es el harness.

  • El modelo decide qué herramienta y con qué argumentos
  • El harness ejecuta y agrega el resultado al contexto
  • Después el modelo vuelve a ser llamado con ese resultado
CU-02 «Consultar matrícula». Unificar el término harness desde aquí.

Agente: un modelo que dirige un bucle

  • Un agente es un LLM que dirige dinámicamente sus pasos y herramientas: decide, actúa, observa y repite. Lo ejecuta un harness (Acto 6: agente = modelo + harness)
  • Un workflow, en cambio, sigue pasos fijados por el código
  • El bucle termina cuando el objetivo se cumple o cuando se alcanza un tope
Fuente: Anthropic, «Building effective agents».

    RAG: recuperar por cercanía

    • RAG significa Retrieval-Augmented Generation: generación aumentada por recuperación. Antes de responder, se buscan documentos relevantes y se agregan al contexto del modelo
    • Se recuperan los documentos más cercanos a la pregunta
    • Es la misma operación del detector de saludos: cercanía entre embeddings
    • Permite responder con documentos propios (programa, reglas, SRS) y citar la fuente
    • Si la recuperación falla, responde con lo equivocado, y puede alucinar igual

      MCP: un protocolo abierto para conectar herramientas

      • Model Context Protocol: estándar abierto para conectar aplicaciones de IA con herramientas y datos externos
      • Analogía: el USB-C de la IA, un solo conector en vez de una integración a medida por herramienta
      • No es «modelos personalizados»: es un protocolo
      • Amplía la superficie de ataque: se revisa cada servidor antes de conectarlo
      Confirmado en modelcontextprotocol.io. Donado a la Agentic AI Foundation (Linux Foundation) el 9 de diciembre de 2025.

              Spec-Driven DevelopmentNo es documentación que se escribe y se olvida: es un artefacto vivo que guía al agente.

              SDD no es Waterfall

              Waterfall
              • Plan exhaustivo antes de codificar
              • Fases secuenciales rígidas
              • El cambio es costoso
              SDD
              • Spec mínima y suficiente
              • Iterativo: spec, plan, tasks, código
              • La spec evoluciona y el plan se regenera

              Si se planifica en exceso sin validar, SDD puede caer en un neo-waterfall.

              Lugar de SDD respecto de TDD y BDD.

                Ejemplo: plan.md y tasks.md

                # plan.md
- Interface GreetingClassifier with two
  implementations: KeywordGreetingClassifier
  and EmbeddingGreetingClassifier (Strategy).
- POST /api/v1/messages/classify
  -> { "isGreeting": boolean, "confidence": number }
- React component GreetingChecker (strict types).

# tasks.md
1. Create ClassificationResult + GreetingClassifier.
2. KeywordGreetingClassifier + parameterized test.
3. Expose the endpoint + controller test (Mockito).
4. EmbeddingGreetingClassifier behind the interface.
5. GreetingChecker in React/TS + component test.

                El plan aplica Strategy e inversión de dependencias (Módulo 5); las tareas son pequeñas y probables.

                • Las tareas 2 y 4 comparten el mismo set
                • Cambiar de clasificador no toca el controlador
                Un solo archivo tasks.md, no una carpeta de tareas.

                Qué verifica a qué

                @ParameterizedTest
@CsvFileSource(resources = "/greetings.csv",
               numLinesToSkip = 1)
void classifiesGreeting(String message, boolean expected) {
    var result = classifier.classify(message);
    assertEquals(expected, result.isGreeting());
}

                Cada criterio de aceptación se convierte en una prueba. El set de 12 (datos sugeridos) alimenta una prueba parametrizada de JUnit 5.

                • Las pruebas verifican lo que la spec promete
                • La revisión humana verifica lo que la spec no cubre
                • Si cambia el requerimiento, se cambia la spec y se regenera el plan
                Cierre de calidad. Mockito aparece en la prueba del controlador.

                Cuándo usar SDD y cuándo no

                Conviene
                • Funcionalidades con varios actores
                • Trabajo en equipo o con agentes
                • Cuando el qué debe quedar verificable
                No conviene
                • Un bug menor
                • Un experimento descartable
                • Cuando la spec costaría más que el cambio

                La spec también puede estar mal: el humano la revisa.
